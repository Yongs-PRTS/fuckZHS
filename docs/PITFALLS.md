## 1. 作业提交 0 分：一题没填就提交了

**现象**：做完第五章单元测试，页面显示已提交，成绩 0/70，服务端 `achieveCount=1`（只算了一道）。

**原因**：

- 填答案的循环遇到「选项集合和题目对不上」时直接 `break` 跳出；
- 跳出后**没有任何完整性检查**就调用了提交接口；
- 提交时页面还停在上一题的过渡动画里，新题的 `input` 还没渲染出来。

**处理**：

- 新增 `wait_for_question()`：提交一题后轮询 12 秒，等下一题真正渲染出来；
- 提交前守卫：`filled == len(answers) == total_expected` 三者相等才允许提交，否则**拒绝提交**；
- 已答过的题（页面上已有选中项）直接跳过；
- 选项集合对不上时重试，不再 `break`。

**验证**：本地 HTML 夹具模拟一套题（101/102/103 单选，201/202/203 多选），逐题点击后读 `checked`，确认没有被提前提交。

## 2. 多选题永远不答

**现象**：单选正常，一到多选就跳过，整份作业卡住。

**原因**：所有选择器只匹配 `input[type=radio]`，多选用的是 `input[type=checkbox]`，一个都选不中。

**处理**：选择器改成 `input[type=radio], input[type=checkbox]`；点击目标从隐藏的 `input` 改成可见父级 `div.fl.ffff`，点不动再回退到直接设置 `checked`。

**验证**：夹具里多选三道全选，读取 `checked` 全为真。

## 3. 答题页停在 about:blank

**现象**：点开始答题，弹出的 Edge 一直停在空白页。

**原因**：上一次被强杀留下的 Edge 还占着固定调试端口 `9333`，新进程连上的是僵尸浏览器。

**处理**：

- 端口改成每次**随机取一个空闲端口**；
- 启动前 `kill_orphan_browsers()`，按临时 profile 前缀清理残留；
- 开窗后 `Page.bringToFront` 确保到前台。

**验证**：连续启动多次，`/json/list` 里始终只有本次窗口。

## 4. 易盾点选验证码：接口路线走不通

**现象**：接口答题时只返回一行：

```json
{"status":"-1","msg":"滑块验证未通过，不能答题"}
```

没有挑战图，也没有票据。

**排查**：直接调 `saveAnswer` 不带 challenge、换 UA、换 Origin/Referer、重新 SSO 拿新票，全部同样被拒；网页端确实会弹易盾点选（页面里有 100 多个 `.yidun` 元素）。

**结论**：这是**账号级风控**，没有可编程的通过路径。

**处理**：产品形态改成**半自动**——程序取题、生成答案、点选项、切下一题；验证码留给人在真实浏览器里点一下，程序检测到通过后自动继续。

**验证**：人工点掉验证码后，程序能继续填完全部题目。

## 5. 学生中心改版导致打不开答题页

**现象**：状态显示「作业处理完成：1 份，共填 0 题」，但日志里 5 道答案都生成好了：

```
[1/5] 单选 D = 564907124 => ①③
  点击「作业考试」：no-name-node
! 没能打开答题页
```

**原因**（两个叠加）：

1. 打开学生中心后**固定 `sleep(8)`** 就去找课程节点，而实测 8 秒时页面还在 `interactive`，课程名约 11 秒才出现；
2. 课程卡结构改版：新版是 `.hoverList > dl > dt > .item-left-course > .courseName`，而「作业考试」是**悬停才出现的浮层**，不在卡片内部。旧代码在卡片里找 `.course-menu-w`，永远找不到。

**处理**：

- 去掉固定等待，改成**最多轮询 45 秒**；
- 先派发 `mouseenter/mouseover/mousemove` 让浮层出现，等 0.9 秒再点；
- 菜单共 12 个（3 门课 × 4 个），按课程在 `.hoverList` 里的**下标**取对应的「作业考试」；
- 文本匹配改成「相等 → 前缀 → 包含」三级回退，并处理全角空格；
- 失败时把页面真实文本打进日志。

**验证**：真实 Cookie 跑 `open_exam_page`，53.9 秒后落到答题页，5 道题正常显示。顺带把开头的 8 秒降到 2 秒（有轮询兜底）。

## 6. CDP 命令 60 秒超时

**现象**：

```
File "homework_browser.py", line 272, in open_exam_page
File "homework_browser.py", line 95, in send
websocket._exceptions.WebSocketTimeoutException: Connection timed out
```

**原因**：

- `Cdp.send()` 只有连接级 60 秒超时，**没有单条命令超时**；
- 完全没处理 JS 对话框——页面弹 `alert`/`confirm` 会挂起渲染进程，CDP 永远等不到回包；
- 浏览器被关掉时也照样傻等。

**处理**：

- 每条命令独立超时：默认 20 秒，`Page.navigate` 45 秒；
- 监听 `Page.javascriptDialogOpening`，自动 `handleJavaScriptDialog(accept=true)`；
- `Cdp` 持有浏览器进程句柄，`proc.poll()` 不为空立刻抛 `BrowserGone`；
- 底层异常翻译成人话：「浏览器那边出问题了：… 请关掉弹出的 Edge 窗口后重新开始」。

**验证**：

| 场景 | 结果 |
|---|---|
| 普通命令 | 正常 |
| 页面带 `alert` 时导航 | 0.0 秒返回，之后脚本照常执行 |
| 中途杀掉浏览器再发命令 | 立刻抛「浏览器窗口已经关闭」（0.02 秒） |

## 7. 写进代码的正则丢了反斜杠

**现象**：课程名匹配时灵时不灵。

**原因**：写进源文件的 JS 成了 `replace(/s+/g, '')`——反斜杠在多层转义里丢了，等于**把字母 s 当空白删掉**。课程名带 `s` 就错位。

**处理**：不用正则，改成按字符码过滤：

```js
const strip = (t) => [...(t || '')]
  .filter((ch) => ch.charCodeAt(0) > 32 && ch.charCodeAt(0) !== 12288)
  .join('');
```

`12288` 是全角空格。整段 JS 里再没有反斜杠，转义失效也不会踩。

**教训**：跨语言写正则，宁可不用正则。

## 8. 桌面窗口：无边框改造的三次翻车

背景：想把窗口做成「左边没有图标和标题、右边保留系统三键、标题栏雾面」。中间连续踩了三个坑。

### 8.1 第一版：`ShowIcon = False` 把窗口搞死

**现象**：窗口出来但完全不响应，Windows 事件日志里是 `AppHangB1`。

**原因**：从后台线程设置 WinForms 属性会触发**窗口句柄重建**，而句柄上挂着 WebView2，重建期间 UI 线程直接锁死。

**处理**：放弃改 WinForms 属性，图标改用启动参数（见 8.3）。

### 8.2 第二版：`SetWindowPos(FRAMECHANGED)` 同样危险

**原因**：改窗口样式（`WS_EX_DLGMODALFRAME`）再 `FRAMECHANGED`，会强制非客户区重算并让 WebView2 子窗口跟着 resize，初始化期间同样可能锁死。

**处理**：所有 `SendMessage/SetWindowPos` 全部删掉，改成「只发最轻的消息都不发」。

### 8.3 稳定版：透明图标 + 官方接口清标题

- **图标**：用 PIL 生成一张全透明 ico，通过 `webview.start(icon=路径)` 传入——WinForms 在**创建窗口时**自己设置，不跨线程发消息；
- **标题**：`window.title = ""`，走 pywebview 自己的 `set_title`，内部会切到 UI 线程；
- **圆角/雾面**：只调 `DwmSetWindowAttribute`（33 圆角、38 Mica），不碰窗口消息。

**验证**：`WM_GETICON` 返回 0、`MainWindowTitle` 为空、三键保留、`IsHungAppWindow=False`。

## 9. 启动偶发卡死 AppHang

**现象**：用户点了很久没反应；机器上只剩一堆孤儿 `msedgewebview2` 进程。

**排查**：

1. Windows 事件日志：3 次 `AppHangB1`；
2. 用 `faulthandler.dump_traceback_later` 抓线程栈，UI 线程停在 pywebview 的 `winforms.py:808 app.Run()`（消息循环里）；
3. 逐项关闭可疑代码（标题栏美化、模块预热）→ 仍然偶发 → 说明**不只是我们的代码**。

**关键发现**：`webview.start(func)` 的 `func` 其实是在 **UI 线程**上执行的（pywebview 用定时器触发）。我在里面 `sleep` + 轮询窗口，等于把窗口冻住十几秒——这是最初那次「点了没反应」的直接原因。

**处理**：

- 美化改成挂 `window.events.loaded`，且只做一次；回调里只**起后台线程**，绝不阻塞；
- 新增**缓存自愈**：启动写 `runtime/webview.dirty`，正常退出才删；下次启动发现它还在，就丢掉 WebView2 缓存重建；
- 新增**启动看门狗**：窗口连续 15 秒无响应就弹提示并退出，不再让人对着冻住的窗口点。

**结论**：卡死有两层——(a) 我们自己的阻塞代码；(b) WebView2 初始化偶发挂起（环境相关，杀软/残留进程会放大）。前者已根除，后者用自愈 + 看门狗兜住。

## 10. 打包版接口卡 6 秒

**现象**：源码版 `GET /api/settings` 125ms 返回；打包版超时 6 秒。

**原因**：处理函数里 `from homework import env_var` 是**运行时导入**。打包版首次 `import homework` 会连带 `fucker`、`openai`、`PIL` 等，慢到被当成卡死。

**处理**：把 `env_var()` 下沉到轻量模块 `app_config.py`，请求路径不再导入重模块。

**验证**：打包版 `GET /api/settings` 回到 125ms。

**插曲**：曾用「后台线程预热 import」来优化首次测试连接，结果它和窗口初始化抢 import 锁，制造了新的卡死竞态 —— 已移除。**不要在启动路径里偷偷 import 重模块。**

## 11. 进程环境变量里读不到用户环境变量

**现象**：用户明明用 `setx` 设了 `DEEPSEEK_API_KEY`，程序里 `os.environ.get(...)` 却是空。

**原因**：进程是由别的宿主拉起的，继承到的环境块可能不含后来设置的用户变量。

**处理**：`env_var()` 先读 `os.environ`，读不到再查注册表 `HKEY_CURRENT_USER\Environment`。

**验证**：`/api/settings` 返回 `has_key: true, key_source: env, env_var: DEEPSEEK_API_KEY`。

## 12. API Key 差点进仓库

**风险**：答题走的是用户自己的 API，Key 一旦写进 `config.json` 又被提交，就直接泄露。

**处理**：

- `.gitignore` 覆盖 `config.json`、`config.json.*`、`cookies.json`、`execution.json`、`logs/`、`runtime/`、`_zhs_archive/`；
- 答题模型改成**界面里填**：服务商预设 + 地址 + 模型 + Key，保存在本机 `config.json`；
- 接口只回**掩码**（`sk-tes…3456`），日志里也只有掩码；
- 提供「测试连接」「清除 Key」，没配置时开始答题会被前后端双重拦下；
- 全仓扫描 `sk-[A-Za-z0-9_-]{16,}`，结果 0 命中。

**地址规范化**（为了能接任何 OpenAI 兼容服务）：

| 用户填的 | 实际请求 |
|---|---|
| `https://api.deepseek.com` | `…/v1/chat/completions` |
| `https://api.openai.com/v1` | `…/v1/chat/completions`（不再重复拼 v1） |
| `https://open.bigmodel.cn/api/paas/v4` | `…/v4/chat/completions` |
| `http://127.0.0.1:11434/v1` | `…/v1/chat/completions` |

## 13. 前端可读性与交互反馈

**现象**：用户反馈「字体不清晰、交互不明显」。

**量化**：全站有 **54 处字号 ≤10px**（最小 7px）；`:active` 状态**一条都没有**，`:hover` 只有 12 处。

**处理**（只动可读性与反馈，不改配色和版式）：

- 字号整体上移一档：7→9、8→10、9→10.5、10→11.5、11→12（共 83 处）；面板高度只增加 3.5%；
- 次级文字提亮 22 处（如 `#777d73 → #8f978a`）；
- 补齐交互态：按下下沉 1px、悬停加底、输入框聚焦酸性绿边框 + 3px 光晕、禁用 45% 透明 + `not-allowed`、统一 0.16s 过渡、数字用等宽字形；
- 顺手修掉状态卡「标题和正文都是『等待操作』」的重复文案。

**验证**：CDP 强制伪类读计算样式：`hover` → `translateY(-2px)`、`hover+active` → `translateY(1px)`、`focus` → 酸性绿边框 + 光晕、`focus-visible` → 2px 描边。

## 14. 日志行多出一截毫秒数字

**现象**：日志里出现 `173:` 这种奇怪前缀。

**原因**：解析正则把时间后的毫秒片段当成了消息内容。

**处理**：`LOG_LINE_RE` 改成容忍可选毫秒：`^(\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2})(?:,\d{3})?:\s{0,2}(.*)$`。

## 15. 验证手段沉淀

这个项目 GUI 多、外部依赖多，肉眼验证不可靠。最终沉淀了这几招：

| 手段 | 用途 |
|---|---|
| 本地 HTML 夹具 + CDP 点击 | 验证单选/多选/提交守卫，不碰真实账号 |
| headless Edge + CDP 截图 | 看界面实际渲染效果，可固定视口做窄屏检查 |
| `CSS.forcePseudoState` | 验证 hover/active/focus 是否真的生效（`document.hasFocus()` 在无头下是 false，直接点不出来） |
| `IsHungAppWindow` + `SendMessageTimeout` | 判断窗口是否真的卡死 |
| `faulthandler.dump_traceback_later` | 卡死时抓全线程栈，定位到具体文件行 |
| 真实请求打接口 | `curl`/`Invoke-RestMethod` 直接验 `/api/*`，不看代码猜 |
| 全仓敏感词扫描 | 提交前确认没有 Key / Cookie |

## 16. 几条通用教训

1. **任何跨进程/跨线程的等待都要有上限**：CDP、HTTP、窗口消息，全部独立超时。
2. **不要在 UI 线程里睡觉**：pywebview 的 `start(func)` 回调就在 UI 线程上，`sleep` 等于冻结窗口。
3. **不要改正在承载 WebView2 的 WinForms 窗口属性**：句柄重建 = 卡死。用启动参数和官方接口。
4. **启动路径别做重活**：不在请求处理函数里 import 大模块，不在启动时抢锁。
5. **对不可控的外部环境做兜底**：缓存自愈、看门狗、友好的错误文案，比 traceback 有用得多。
6. **失败要留下可诊断的信息**：把页面真实文本、当前 URL 打进日志，比「失败了」有价值一百倍。
7. **改选择器前先看真实 DOM**：网页改版是常态，别凭记忆写 XPath/CSS。
8. **验证要能复现**：能用一个夹具/一条命令证明修好了，才算修好。
