# 桌面启动无响应修复（2026-10-29）

快捷方式：`E:\桌面\ZHS.lnk`，目标为本项目 `dist\ZHS-Desktop.exe`，工作目录为 `dist`。

## 已确认的问题

- `DesktopApi.window` 是公开属性。当前安装的 pywebview 6.2.1 在生成 JS 桥接 API 时，递归遍历公开对象并执行属性 getter，因此会进入 `Window`、WinForms 和 WebView2 对象。启动时不应对原生窗口进行这种反射。改为私有引用 `_window`，桥接仅导出 `resize`。
- 没有单实例保护。重复启动会共同访问任务状态和 WebView2 profile；第二个实例看到第一个实例创建的 `webview.dirty`，会直接尝试删除仍在使用的缓存。新增 Windows 文件锁，在配置、任务管理器、服务和 WebView 初始化前获取，并保持到退出清理完成。再次打开只尝试恢复已有窗口。
- 原看门狗在第一次检测正常后直接返回，不能检测随后发生的卡死。改为持续监测整个启动观察期（约两分钟），窗口关闭时取消；持续无响应时记录线程栈。

## 缓存和诊断

异常退出后改用新的 `runtime/webview-recovery-*` 目录，保留可能仍被残留 WebView 进程占用的旧缓存，避免启动时同步递归删除。正常退出后复用选定 profile。账号 Cookie、配置和课程清单仍在 exe 同目录。

启动与退出事件记录在 `dist/runtime/desktop.log`，日志自动轮换；检测到持续无响应时线程栈记录在 `dist/runtime/stacks.txt`。

## 可复现检查

运行 `.venv\Scripts\python.exe tools/test_desktop_startup.py`：

1. 使用 pywebview 实际桥接生成函数，证明旧的公开窗口引用被递归访问，而新版本只导出 resize。
2. 用独立进程验证重复启动互斥、正常释放，以及 `os._exit` 异常退出后自动释放锁。
3. 模拟异常退出，验证旧缓存内容保留、新缓存隔离、正常退出后复用新缓存。
4. 模拟首次正常、随后连续无响应，验证看门狗仍能检测。

四项均通过。原 exe 本次单次启动正常，未直接重现用户报告的偶发 AppHang；上述回归验证的是已确认的启动缺陷，不能据此保证所有机器上的 WebView2 问题均已消失。
